# DirectMusic Producer 解析と再構築の実施計画

作成日：2026-10-02（日本時間）

対象：DirectX 9 用 DirectMusic Producer 5.3.0.900

## 採用する進め方

本体からモジュールの生成・接続・終了の流れを把握し、最初の詳細解析と再実装は `TempoStripMgr.dll` を対象にする。一つの機能ごとに「原版で観測する → 仕様を記録する → 実装する → 同じ入力で比較する」を繰り返し、本体上での置換が成立してから対象を広げる。

| 順序 | 到達点 | 判定に使う成果 |
| --- | --- | --- |
| 1 | 調査を再開できる基準を作る | 元ファイルの識別情報、依存一覧、抽出手順 |
| 2 | 本体と最初の DLL の接続を説明できる | 生成経路、インターフェース、所有権、未確定事項 |
| 3 | 原版の結果を繰り返し取得できる | 固定した試験環境、最小入力、操作手順、保存結果 |
| 4 | 最初の DLL をソースからビルドして比較できる | 接続仕様、実装、比較ハーネス、差異と未対応機能 |
| 5 | 本体上で最初の DLL を置換できる | 表示・操作・保存・再読込の統合結果、原版へ戻す手順 |
| 6 | Producer 全体を再構築できる | 全対象のソース、クリーンビルド、編集・再生の受入試験 |

各工程の具体的な作業と完了条件は後述する。直近の作業は「直近の作業単位」、全体の合否は「全体完成時の受入試験」で管理する。未確認の機能を完成扱いにせず、次の調査で何を確かめるかを残す。

## 現在の到達点

起動時のレジストリ警告について、公式署名付きAutoItのポータブル版で対象PID・EXE・警告文・実OKボタンを照合し、撮影、自動OK、続く原版編集画面を確認した。実ボタンはID2で、DPI倍率による撮影座標の差も修正した。以前のC++補助EXEの実行拒否を保持し、今後の起動試験は確認済みのAutoIt手順を使う。[撮影・自動OKの記録](analysis/producer-startup-dialog.md) にコード、公式資料、成功・失敗ログと再実行方法を残した。全体再構築の完了条件は変更しない。

TimeSigStripMgrはFramework・再生トラックの参照管理に加え、試験用Timelineへの接続・切断とStripの基本プロパティを実装した。保存17ソースからビルドした候補630bで、11接続ケース・20プロパティを含む160観測と、既存322観測・196時刻問合せ・27入出力ファイルが原版と正規化なしで一致した。接続比較器の7テストが成功し、共通CMakeの保存48ファイルから全11ターゲットのビルドも確認した。以前の別ハッシュの生成物のOS拒否は履歴として保持する。今回比較したのはStyle管理対象の検索が失敗する接続経路であり、実Timeline・Style拍子データの取込み・編集UI・通知配送・ランタイム同期と本体置換は未確認である。[拍子モジュールの根拠と残作業](analysis/time-signature-strip-manager.md) を記録した。互換ソースは2モジュールの限定経路だけであり、工程6・全体再構築は完了していない。

参照保持の追加調査では、原版TimelineのExport処理がアンロード用カウンターを増やし、返したIDataObjectの破棄経路に対応する直接減算がないことを静的に確認した。動的診断でも、原版・候補ともExport4回後、全所有者とOLEの解放後にカウンター4が残った。アンロードS_FALSEと生存COM参照の漏れを区別する。[寿命の調査](analysis/timeline-clipboard-lifetime.md) に固定バイナリの命令照合と同一36ソースによる観測を残した。

本計画は、本体で全体構造を把握した後、小さな DLL を詳しく解析し、再実装と比較検証を通じて対象を広げるための手順を定める。最初の到達点は、候補である `TempoStripMgr.dll` について、原版と接続できる仕様と、ソースからビルドできる代替実装を得ることである。

長期的には Producer 全体をソースからビルドし、プロジェクトの編集・保存・再読込・再生を検証できる状態を目指す。原版ソースは未取得のため、同じソースや同一バイナリの復元を前提にはしない。仕様の復元と互換実装を進め、原版ソースやヘッダーが見つかった場合は、その内容と適用条件を確認して計画へ反映する。

## 作業の基本方針

- `artifacts/` は取得物の保管場所とし、パッチや解析結果で上書きしない。バイナリの加工、デバッガーのデータベース、試験実行は `work/` で行う。
- 原版との接続検証は x86 を基準にする。初期段階では x64 化や UI の全面刷新を同時に進めない。
- `MFC42.DLL`、`MSVCRT.DLL` などは依存ライブラリとして識別し、まず Producer 固有コードの解析に集中する。呼び出し規約やデータ配置に関係する部分は調査対象に含める。
- 結論を「資料の記述」「静的に確認」「動的に確認」「仮説」に分ける。推定した関数名や型は、根拠と未確認点を併記する。
- 各工程の完了は成果物と検証結果で判断する。逆コンパイルできた関数数だけでは進捗を評価しない。

## 工程と完了条件

### 工程0 解析の基準を固定する

**目的：** 別の作業日や環境でも、同じ入力と手順から調査を再開できる状態にする。

実施内容：

1. マニフェストと作業コピーを照合し、対象 EXE/DLL/OCX の SHA-256、サイズ、PE アーキテクチャ、バージョンを一覧化する。
2. インポート、エクスポート、セクション、リソース、文字列、デバッグ情報の有無を抽出する。既に利用可能な LLVM ツールから始め、逆アセンブラ・デバッガーは必要機能と利用可能性を確認して選ぶ。
3. 同梱 CHM、README、サンプルから、起動、編集、保存、再生の基本操作とファイル形式の手掛かりを整理する。
4. ツールのバージョン、コマンド、出力先を記録する。資料や公開 SDK の追加探索では、取得元・版・該当箇所を記録する。

成果物：`docs/analysis/baseline.md`、`docs/analysis/modules.csv`、抽出用スクリプト、`work/analysis/` 内の抽出結果。

**完了条件：** 対象ファイルをハッシュで特定でき、主要な抽出処理を再実行できる。資料から得た事実と、これから調べる事項が区別されている。

### 工程1 本体から接続関係を把握する

**目的：** DLL を読むために必要な本体側の構造を把握する。本体全体の詳細解析はここでは行わない。

実施内容：

1. MFC の初期化経路から、アプリ固有の初期化、コンポーネント探索、生成・終了処理を追う。
2. `CoCreateInstance`、動的ロード、レジストリ参照の呼び出し元を確認し、クラス識別子と候補モジュールを対応付ける。
3. ファイルを開く操作から、プロジェクト・文書・編集モジュールへの振り分けを追う。
4. 本体がモジュールへ渡すサービスと、モジュールが本体へ返すインターフェースを整理する。
5. TempoStripMgr に至る経路について、本体、SegmentDesigner、Timeline などがどう関係するかを調べる。関係が未確認の箇所は図でも未確定と示す。

成果物：`docs/analysis/host-map.md`、`docs/analysis/com-interfaces.csv`、識別子と根拠アドレスの一覧。

**完了条件：** 最初の対象モジュールの生成経路と主要な接続先について、根拠付きの見取り図がある。静的情報だけでは決まらない点は工程2の観測項目に落とし込まれている。

### 工程2 原版の動作を比較基準にする

**目的：** 再実装の正しさを判断できる原版の入力と出力を確保する。

実施内容：

1. 原版を実行する復元可能な試験環境を用意し、OS、x86 実行環境、DirectMusic ランタイム、COM 登録、フォント等の条件を記録する。実際に使用する構成は調査後に選定する。
2. インストーラーによる配置と登録を観測する。現在の `app/` は解析用配置なので、正式なインストール結果との違いを確認する。
3. 原版の起動、サンプルの読込、編集、保存、再読込を順に確かめる。再生は別項目として確認し、音が出ないことと文書編集の失敗を混同しない。
4. テンポ変更の最小入力を作り、操作手順、保存データ、戻り値、通知、終了時の状態を、観測可能な範囲で記録する。
5. デバッガー等で工程1の生成経路と呼び出し順序を確認する。

成果物：`docs/analysis/reference-environment.md`、`docs/analysis/reference-cases.md`、`work/reference/` 内の試験入力・出力・ログ。

**完了条件：** 初回の置換対象について、原版で同じ試験を繰り返せる。少なくとも生成・終了、基本編集、保存・再読込の結果が残っている。未観測項目は明示されている。

工程0の後は、工程1と独立する環境準備を進めてよい。原版の実行に詰まった場合は工程3の静的解析を続けるが、比較試験や互換性確認が済んだとは扱わない。

### 工程3 TempoStripMgr の接続仕様と動作を復元する

**目的：** 一つのモジュールについて、実装可能な仕様を得る。

実施内容：

1. クラスファクトリーから生成されるオブジェクト、`QueryInterface` の対応 IID、参照カウント、主要な仮想関数テーブルを整理する。
2. メソッドごとに引数、戻り値、構造体の配置、文字列の表現、メモリの所有権、呼び出し順序を調べる。COM 集約やスレッド条件が関係するかも確認する。
3. テンポイベントの管理、選択、追加・変更・削除、通知、保存・読込を追う。Undo やコピー操作は存在と責務を確認して試験項目に加える。
4. 呼び出される側の Timeline や本体サービスは、必要なインターフェースから調べる。依存先全体の解析へ際限なく広げない。
5. 公開資料やヘッダーに対応する宣言が見つかれば、バイナリの版と照合する。IID やメソッド名が似ているだけでは同一仕様としない。

成果物：`docs/analysis/tempo-strip-manager.md`、根拠付きのインターフェース宣言、関数対応表、対象機能一覧。

**完了条件：** 最小の生成・接続・編集・保存・解放経路について、実装を妨げる未確定の型や所有権が解消されている。それ以外の未解明機能は範囲を明示して残せる。

**対象の見直し条件：** TempoStripMgr に未知の大規模な依存が集中していると判明した場合は、ほかの小さな StripMgr と接続先の数、状態の複雑さ、試験可能性を比較する。選定理由と既存成果の再利用先を記録して対象を変更する。単に逆コンパイル結果が読みにくいという理由だけでは変更しない。

### 工程4 比較用ハーネスと最小の代替実装を作る

**目的：** 復元した仕様を実行可能な形で確かめる。

実施内容：

1. ネイティブ C++ / x86 を初期候補に、原版との境界を再現できるビルド構成を決める。必要なら MFC 等の依存条件を先に検証する。
2. 原版と代替実装に同じ入力を与える試験プログラムを作る。最初は生成、インターフェース取得、参照管理、終了を対象にする。
3. テンポイベントの追加・変更・削除、保存・読込へ順に広げる。原版を直接呼べない部分は、本体上の操作試験を利用する。
4. 通常ケースに加え、空データ、境界位置、重複、範囲外値、途中で切れた入力などを、実際の仕様に応じて選定する。
5. ハーネスが模倣した本体サービスについては、何を省略しているかを記録する。ハーネスの成功だけで本体との互換性を結論付けない。

成果物：`src/` 内の実装、`tests/` 内の比較ハーネス、ビルド手順、`docs/analysis/tempo-comparison.md`。

**完了条件：** 手作業でバイナリを修正せずにソースからビルドでき、定義した最小機能の比較試験が通る。原版に依存する未実装部分が明示されている。

保存データは、まず意味上の一致と相互読込を確認する。日時や識別子などの可変値が存在する場合は、正規化の理由と対象を記録する。差を隠すための無条件な除外はしない。

### 工程5 原版の本体へ接続して検証する

**目的：** 単体での一致を、本体上での実用的な互換性につなげる。

実施内容：

1. 試験環境に置換前の状態を残し、対象モジュールだけを代替実装に切り替える。登録や配置の変更内容を記録する。
2. 生成・終了、テンポ編集、保存・再読込、原版との相互読込を確認する。Undo、選択、コピー、再生への反映は、原版で確認した責務に応じて追加する。
3. 複数文書、繰り返しの開閉、エラー入力を試し、状態の混入、参照管理、通知順序の問題を調べる。
4. 失敗時は原版へ戻して同じ入力を試し、原版の制約と代替実装の不具合を分ける。

成果物：`docs/analysis/tempo-integration.md`、実行ログ、既知の差異と残作業一覧。
