開始時にリポジトリの指示、現行計画、docs/analysis/plan-review-2026-10-05.md、product-state.jsonとそこから参照する最新単位を確認してください。既存変更・失敗履歴・成果物を保持し、履歴にある古い「次の作業」は実行指示として扱わないでください。

通常coreに含まれない専用試験も列挙したregression-manifestと、全体8受入の状態表を作り、固定候補で回帰を一巡してください。未実行・障害・失敗を合格に含めないでください。状態整理だけで終わらず、判明した不整合を修正してください。

その後はQ1の本体統合、Q2の原版なし環境、Q3の未着手責務、Q4の最終受入へ進んでください。Q1では同一候補・同一シナリオで、新規native Project、読込・編集・Undo/Redo・保存・正常終了・別プロセス再読込・再生/停止/再開・テンポ音声まで証拠を接続してください。原版を配置しない環境が未用意なら障害を明記し、独立したQ3を進めてください。

各作業で対象機能、閉じる受入の不足、必要な変更・試験・終了条件を定め、その単位を完了してください。関連しない細部へ際限なく広げず、新しい残課題はqueueに残して次の優先責務へ進んでください。同じ群の細分化が続いて全体の不足が減らない場合は、計画の見直し基準に従って優先順位を更新してください。

原版観測→契約→実装→本体操作/保存復元→比較を機能単位で進めてください。独立RIFF監査や録音解析を原版動的比較の代わりにせず、未知データ保持だけで対応済みとしないでください。台帳の古い「未着手」に従って既存実装を作り直さないでください。

音声は既存WASAPI自動録音・解析で確認し、人の聴取待ちを前提にしないでください。OS拒否を迂回せず、同一条件の失敗再試行を繰り返さず、独立した作業を続けてください。既存承認を尊重し、確認が必要な場合のみ対象・理由・判断事項を具体的に示してください。

終了時には候補、変更、検証結果、残責務・原版依存、次の具体的な一手を最新単位と状態表に保存してください。計画書には時系列ログを追記せず、現在のqueueと判断だけを更新してください。全体の全責務と受入8項目が同じ最終構成で合格したときだけ目標を完了にし、再現可能なbuild/install/検証手順と証拠を提示してください。
